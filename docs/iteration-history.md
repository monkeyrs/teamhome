# TeamHome 迭代历史

> 用途：面向项目成员的阶段总结文档。若要生成示例团队种子数据，请优先参考 [onboarding-content.md](onboarding-content.md) 里的短时间线版本。

## 说明

这份文档基于以下可核验证据整理：

- `teamhome` 仓库的 Git 提交记录
- `README.md`、`docs/assistant-ai-plan.md`、部署文档等项目内文档
- 当前代码目录结构与文件落地情况
- 本轮连续对话中已经明确并落地的产品、架构与交互调整

它适合作为“基于仓库与迭代事实的阶段总结”，不等同于完整会议纪要或全部聊天原文归档。

## 总体判断

从 Git 历史和本轮连续迭代看，`TeamHome` 的核心开发集中在 2026-03-19 到 2026-03-28 之间。项目在极短时间内完成了：

1. 基础前后端骨架搭建
2. 日程 / 费用 / 团队协作主流程落地
3. 助手从问答入口升级为业务编排入口
4. i18n 与多语言能力补齐
5. LangGraph、LangSmith、模型容灾、导出、分析页等增强能力接入
6. Docker 部署、脚本与生产域名路由收口

项目主线很清晰：先把“团队/家庭协作 + 日程 + 记账”的基础产品跑通，再把“助手”从聊天页升级为受控执行的业务编排层。

## 本轮对话补充明细

### 助手产品定位继续收口

- 助手被进一步明确为“日程 + 费用助手，可少量闲聊”。
- 核心能力持续围绕四类技能收敛：
  - 创建日程
  - 查询日程
  - 创建费用 / 收入
  - 查询费用
- 一句话可能同时包含多个意图，因此编排要求从单 intent 识别升级为“多 intent 解析 + 顺序执行”。
- 查询 / 聊天类允许保留上下文；创建 / 更新类要求隔离上下文，避免互相污染。

### 助手页交互经历了多轮收紧

- 回答区右上角从“撤销最近三次”改为：
  - 需要确认时显示“确认 / 取消”
  - 已执行后显示“撤销”
- 确认 / 取消按钮被要求做成紧凑按钮，宽度只随文字和左右内边距变化。
- 补参快捷按钮也统一收紧成相同的紧凑样式。
- 发送按钮增加“停止”语义：
  - 发送后按钮变灰
  - 文案从“发送”切为“停止”
  - 点击停止后，即使后端随后返回，也不再渲染这一轮结果

### 语音输入方案调整

- 放弃直接调用大模型做语音识别。
- 转向优先使用微信官方能力或系统输入法自带语音输入。

### 多语言方案被系统化重构

- 前端被要求统一用 i18n 处理页面文案，避免把文案散落回页面代码。
- 语言选择入口放到首页右上角，支持中文 / English / 日本語。
- 语言偏好与当前登录用户绑定，登录后自动读取此前选择。
- 特别强调编码污染问题：
  - 即使出现污染，也尽量集中在统一翻译包
  - 不要把乱码扩散到业务代码
- 后续又新增了分析页相关 i18n 条目，并把 tabBar 文案一并纳入多语言覆盖。

### LangGraph 编排方向被明确

- 用户明确要求把 `assistant_orchestrator` 引入 LangGraph，并最终接入官方调试链路。
- 编排规则被明确为：
  1. 入参始终带 `Current datetime is {sysdate}`
  2. LLM 先做多技能意图分析和动作拆分
  3. 每一步先补齐参数，但不立即执行
  4. 所有步骤明确后统一记录并统一执行
  5. 执行完成后允许整批撤销
- 设计上明确选择“方案 B”：
  - 子图不直接写库
  - 全部动作补齐后统一 `commit batch`
  - 撤销按钮回滚整批操作
- 同时要求：
  - `loop_count` 受控，最大 10
  - 超过 10 直接提示重新输入，不进入执行阶段
  - routing 必须 deterministic
  - 不允许 autonomous agent 式自行乱跳节点

### LangGraph 中 LLM 的使用点被收口

- LLM 主要只用于两处：
  - `prepare` 节点做意图分析和动作组规划
  - `collect_result` / 最终回复阶段做可读结果渲染
- 相应地，槽位抽取、查询统计等链路逐步改成规则型或受控解析。
- `prepare` 的 prompt 被要求固定包含：
  - 当前时间
  - 可用技能清单
  - 每个技能的用途与入参
  - “语义优先于关键词”
  - 关键词来自 i18n term sets
- 额外要求：
  - LLM 后台始终用英文思考和判断
  - 回答时再按用户语言偏好输出

### session / thread 设计被重新澄清

- 查询 / 闲聊类可以保留上下文。
- 创建 / 更新类上下文不能互相污染。
- 因此前端后续采用双 session 思路：
  - `conversation session`
  - `mutation session`
- 查询切入创建时，需要切新线程；mutation 执行完或取消后，需要清掉对应 session。

### 多段文本解析问题被持续修正

- 曾出现典型错误：
  - 多句输入被错误合并成一个日程
  - 日程标题直接使用整段原文
  - 日程与费用切割不准确
- 随后逐步补了几类修正：
  - 先按句子切 fragment，再逐句规划 step
  - 每个 step 携带自己的 `source_text`
  - 相对时间默认值更贴近日常语义
  - 日程标题清洗时间词、前缀词和拖尾描述
- 在补参阶段又暴露出新的问题：
  - 费用 category 被当成强必填，导致反复追问
  - 追问时没有说明当前追问针对的是哪一小段原文
- 最终又补了两类修正：
  - 费用 category 不再作为强阻塞必填，尽量自动归类或兜底
  - 补参问题改成带上下文引用，例如“关于这段内容：……”
- 还增加了“非事件型生活描述”的排除词，避免把“睡了个舒服的懒觉”误建成日程。

### 助手页视觉与结构持续压缩

- 顶部“助手”“团队空间”等大标题逐步删减，只保留必要信息。
- 当前团队区域被收敛成一行：`当前团队：{团队名} 切换`
- 团队切换展开态和语言按钮样式向日程页顶部看齐。
- 输入框高度压缩成单行，发送按钮同一行右侧占 1/4 ~ 1/5。
- 占位文案改为“例如：今天有什么日程。”并纳入三语 i18n。
- “昵称设计”被取消。

### 数据刷新问题被纳入产品体验

- 用户指出：通过助手创建的日程 / 费用，在切换到对应页面时没有自动刷新。
- 项目随后加入了 team 维度的脏标记刷新机制，使相关页面在 `onShow` 时按需刷新。

### 费用页语义与字段命名经历多轮微调

- “分类”文案被要求改成“性质”。
- “类型”文案被要求改为“收/支”。
- 费用创建时间解析被要求更贴近自然语言：
  - “昨天”应回退到昨天日期
  - “早上”默认 9 点
  - “下午”默认 18 点等更合理时段
- 费用备注倾向保留用户原始输入。
- 费用“收入 / 支出”判断被指出不能只靠关键词，需要结合语义。
- 费用页左滑“复制”按钮被改为蓝色。

### 模型接入与容灾

- assistant 调用的大模型被替换为阿里云 MaaS 兼容 OpenAI 接口。
- 用户给出了完整 workspace、apiHost、openAiCompatible 等接入信息。
- 随后又要求实现“模型额度不足自动切换”的 failover 逻辑，并给出大批候选模型。

### LangSmith / LangGraph 调试链路被打通

- 用户要求在 `.env` 中设置：
  - `ASSISTANT_ENGINE=langgraph`
  - `LANGSMITH_TRACING=true`
  - `LANGSMITH_API_KEY=...`
  - `LANGSMITH_PROJECT=teamhome-assistant`
- 同时要求：
  - 启动 `langgraph dev`
  - 把它纳入本地与 Docker 启动 / 重启脚本
  - 接入官方 LangSmith 调试链路

### 编码一致性被上升为工程规范

- 用户明确要求整体解决前后端通信中的中文乱码问题。
- 规范被整理进项目要求与 README，包括：
  - 前端 JS / JSON / 小程序文件使用 UTF-8 无 BOM
  - 后端源码统一 UTF-8 无 BOM
  - JSON 传输设置 `application/json; charset=UTF-8`
  - 数据库使用 UTF-8 / utf8mb4
- 同时要求：
  - 以后做后端架构修改时，要同步更新 `scripts` 下启动 / 重启脚本
- 到 2026-03-28 的“时间线合并重构”阶段，这套规范被继续落实到具体实现里：
  - 时间线页新增与替换的前端 JS / JSON / WXML / WXSS、i18n 覆盖文件都按 UTF-8 无 BOM 约束处理，避免把中文乱码继续扩散到新页面
  - 新增后端 `timeline` 聚合接口时，同步检查前后端 JSON 传输链路与三语文案接入，保证“统一读模型 + i18n 文案”不再引入新的编码不一致点
  - 因为属于后端架构调整，根目录 `scripts` 下的启动、重启脚本也同步更新，并在重启后额外检查 `timeline` 路由可用性
- 这一轮还新增了 `scripts/ensure_utf8.py` 作为编码检查辅助脚本。

  - 展示一张 LangGraph 示意图
  - 把“下载数据”按钮从助手页移到分析页底部悬浮

### 生产部署与运维操作在本轮中也被反复梳理

- 用户多次要求总结“阿里云轻量应用服务器（Docker）做主机时，如何拉取 Codeup 新代码、重启服务”。
- 同时在本轮里处理过：
  - Docker daemon 未启动
  - Docker Hub 依赖拉取失败
  - 容器内依赖缺失
  - 小程序缓存导致的 401 / 405 假问题

### 正式域名方案从子域名切换为主域名路径收口

- 生产环境最初尝试过独立 API 子域名方案，如 `xcx.your-domain.example`。
- 在证书、DNS 与网关链路反复验证后，最终收口为：
  - 个人网站：`https://your-domain.example`
  - 小程序后端：`https://your-domain.example/xcx`
- 这一调整的直接原因是：
  - 现有阿里云证书已可稳定覆盖主域名
  - 主域名路径反代更适合“同一台服务器既跑个人网站又跑小程序后端”的目标
  - 可以减少子域名证书与合法域名配置的额外复杂度
- 相应地，前端默认生产配置、Nginx 模板与部署文档都被统一改成主域名路径方案。

### 本地调试与线上配置被拆分为“默认正式 + 本地覆盖”

- 为避免每次上线前手工注释、切换 API 地址，项目把环境配置调整为：
  - 仓库默认配置固定指向正式域名
  - 本地使用不提交 Git 的 `local.js` 做覆盖
- 这一机制的目标是：
  - 保持仓库中的正式配置始终稳定
  - 允许本地继续使用 `127.0.0.1:8000` 做联调
  - 避免把开发地址误提交到生产配置
- 这次收口与前面的部署方案是配套关系：部署层走 `https://your-domain.example/xcx`，本地联调层走本地覆盖文件。

### HTTPS、Nginx 与证书链路经过了完整排障

- 在阿里云轻量应用服务器上，项目补齐了：
  - Nginx 安装与基础配置
  - 80/443 端口放行
  - 主站静态站点与 `/xcx/` 反向代理
- 证书签发过程中，HTTP-01 验证多次失败，排查过：
  - `/.well-known/acme-challenge/` 路径
  - `webroot` / `standalone` 验证方式
  - Nginx challenge 路径、系统权限与证书链
- 最终部署验证结果明确为：
  - `https://your-domain.example` 返回 `200`
  - `https://your-domain.example/xcx/openapi.json` 返回 `200`
  - `POST /xcx/auth/login` 通过 Nginx 反代可正常返回 `200`
- 这说明项目已经完成从“服务器 8000 端口直连”向“主域名 HTTPS 反代入口”的迁移。

### 微信开发者工具联调问题被定位为客户端网络链路问题

- 在正式域名链路已经打通后，小程序开发者工具仍反复出现：
  - `ERR_CONNECTION_CLOSED`
  - `ERR_CONNECTION_RESET`
- 后续通过多组对照验证，逐步排除了：
  - 后端接口不可用
  - Nginx 反代错误
  - 服务器 443 未监听
  - 证书链在浏览器侧不可用
- 最终现象归纳为：
  - 服务器本机 `curl` 可访问正式 API
  - PC 浏览器可访问 `https://your-domain.example/xcx/openapi.json`
  - Windows 的 `curl` / `Invoke-WebRequest` / 微信开发者工具请求失败
- 因而本轮结论是：该问题主要属于 Windows 本机代理、TUN、Schannel/TLS 或开发者工具网络环境问题，而不是项目服务端问题。

### 用户身份识别被重新纳入产品规划

- 现状上，项目登录链路已经基于 `openid` 区分用户，但显示昵称仍然使用默认占位值“微信用户”。
- 用户进一步提出：不要继续沿用固定占位昵称，而是切换到微信小程序官方支持的用户头像、昵称获取路径。
- 因此本轮在迭代历史层面形成了新的明确方向：
  - 身份识别继续依赖 `wx.login + openid`
  - 展示昵称与头像要改为基于微信官方允许的用户资料获取能力
  - 不再把“微信用户”作为长期方案，只保留为过渡兜底值
- 在 2026-03-28 的继续收口中，这个方向又被重新调整并部分落地：
  - 最终不再推进头像持久化方案，继续只用 `openid` 做用户识别

- 这意味着该事项已经从“方向确认”推进到“昵称链路已收口、头像方案明确放弃”的状态。

### 一、前端 UI 收口进入高频操作优先阶段

- 整体视觉方向被要求对齐微信小程序设计规范中的 style token 思路，避免页面继续停留在“功能能用但交互松散”的状态。
- 助手页被持续压缩和收口：
  - “回答”区域改为显示最近一次 OpenRouter 返回的文本，而不是固定的兜底文案。
  - 撤销入口从图标方案多轮收口为文字按钮“撤销”，放在回答标题区域，并增加二次确认。
  - 发送按钮增加“停止”语义，保证用户主动取消后，后续迟到返回不再覆盖当前轮次状态。
- 日程页、费用页被改造成统一的“吸顶说明 + 吸顶创建条 + 真实记录流”结构：
  - 顶部说明卡片只保留一行短说明。
  - “创建记录”从完整表单改为上方一条可展开的创建入口，视觉上与记录流连在一起。
  - 创建页与修改页统一为同一套底部弹出表单行为。
  - 修改页底部按钮顺序最终收口为：删除（红）/ 保存（绿）/ 取消（蓝色文字）。
- 记录卡片布局被压缩到更接近表单密度：
  - 备注、地点等字段在日程与费用中统一为左右半宽并排。
  - 费用页备注与地点的左右顺序被调整为与日程一致：备注在左，地点在右。
  - 列表卡片要求尽量显示所有字段，同时保持紧凑，减少不必要的统计汇总块。

### 二、手势与状态设计被重新定义

- 日程页、费用页的左右滑动作都被重构为“高频功能优先”，不再把删除作为默认滑动动作。
- 日程页：
  - 左滑改为状态切换：待处理 / 已处理。
  - 右滑改为修改，继续右滑进入修改弹层。
  - 删除功能收纳进修改弹层内部，通过红色小按钮触发。
  - 状态颜色经历多轮校准后收口为：
    - 已处理：灰色，弱化展示
    - 待处理：蓝色，强调待办
    - 从待处理切到已处理时，左滑动作底色用绿色，表达“完成”
    - 从已处理切回待处理时，左滑动作底色用蓝色，表达“恢复待办”
- 费用页：
  - 左滑改为复制，直接拉起创建弹层并预填当前记录内容。
  - 右滑改为修改，删除同样收纳到修改弹层中。

### 三、日程页加载模型被改造成“今天定位 + 未来窗口预加载”

- 日程列表虽然继续按日期倒序，但不再让用户初次进入页面时停在最顶部的未来记录。
- 页面行为被明确为：
  - 首次进入自动定位到“今天”附近
  - 首屏同时预加载未来 30 天的日程
  - 用户上拉到顶部附近时，再继续按 30 天窗口补未来记录
  - 向下则继续翻看历史记录
- 同期还增加了“只看待处理”筛选按钮，并要求它与日程状态颜色、左滑状态切换保持视觉一致。
- 为了验证这种加载与排序行为，还在 `W` 团队维度补了 30 条测试数据，按“以今日为中心、前后各每 3 天一条”的方式分布。

### 四、i18n 从补丁式修正转向统一治理

- 由于一次 i18n 合并冲突，前端大量此前已经收口的界面行为与文案绑定出现回退，触发了一轮“恢复既有交互 + 补齐 i18n key”的返工。

  - 日程页“只看待处理”
  - 未来加载提示
  - 费用页顶部短说明

  - 后续新增的费用筛选按钮“只看支出 / 只看收入”

- 期间还出现了一个文案语义修正：费用页顶部筛选的“只看费用”被进一步明确为“只看支出”，以避免“费用=所有财务记录”的歧义。

### 五、费用查询接口能力被补齐到“带日期范围”

- 在编排和业务逻辑层面，费用查询原本只有 `question`，没有时间窗口入参，这会导致：
  - REST 查询能力与日程不对齐
  - LangGraph 中 `query_finance` 的 tool schema 无法表达时间范围
  - LLM finance snapshot 只能做全量或模糊回答
- 因此后续补上了完整链路：
  - `GET /finance` 新增 `window_start / window_end`
  - CRUD 查询改为按 `occurred_at` 过滤
  - `answer_finance_question` 支持带时间窗口构建 snapshot 与 fallback 统计
  - `assistant_orchestrator` 中 `query_finance` 的定义、slot 解析和执行链路同步更新
- 这标志着费用查询能力正式从“问题字符串驱动”升级为“问题 + 结构化范围条件”的组合查询。

### 六、本地联调排障最终定位到 Windows 宿主机，而不是业务代码

- 在“小程序请求本地 `http://127.0.0.1:8000/auth/login` 被拒绝”以及 `scripts/start` 报错的排障中，最初怀疑过：
  - 启动脚本写法问题
  - Docker Compose 未生效
  - API 容器未启动
  - 本地前端 `request.js` 配置错误
- 实际排查结论更底层：
  - `backend-dev.ps1` 的问题之一，是对旧容器只做 `docker compose up -d`，不会强制重建已有 `api/langgraph` 容器，已在脚本里补成 `--force-recreate`
  - 但真正导致 `127.0.0.1:8000` 连不通的根因，是当前 Windows 把 `8000` 落进了 TCP excluded port range `7975-8074`
  - Docker 因而无法把容器端口发布到宿主机 `8000`，表现为小程序 `ERR_CONNECTION_REFUSED`
- 这一轮排障的结论非常明确：此处不是 TeamHome 业务代码缺陷，而是本机 Docker 与 Windows NAT / HNS 端口保留策略冲突。
- 同时还确认：
  - 前端本地配置 `frontend/config/local.js` 当前确实指向 `http://127.0.0.1:8000`
  - 因此只要宿主机 8000 不能绑定，小程序本地登录链路就一定失败

  - 微信登录在生产环境下不再允许退回到开发态伪造 `openid`
  - `/assistant/transcribe` 从未鉴权上传改为必须登录，并补上文件类型、大小、空文件校验
  - `finance/schedules` 的 `/parse` 接口补上登录鉴权，避免匿名消耗 LLM 资源
  - `/assistant/orchestration` 调试接口只在显式开启调试时可访问

  - Windows 与 Bash 的启动 / 重启 / 服务器拉起脚本都加入了生产配置预检
  - 在真正 `docker compose up` 之前先校验 `backend/.env` 是否满足正式版安全要求
  - `requirements.txt` 也同步补上了显式直接依赖，避免仅依赖传递依赖链
- 同一轮后端架构收口还补上了几项更偏“正式版稳定性”的基础调整：
  - assistant 的多轮会话状态与 undo 历史从进程内存迁到数据库，避免容器重启、多实例部署或 worker 回收后上下文与撤销记录直接丢失
  - 启动时通过 `create_all` / `schema_sync` 动态补表补列的做法被移除，schema 变更重新收口到 Alembic 迁移，并新增 `0004_add_assistant_runtime_state` 与 `0005_sync_runtime_schema_to_models`
  - 部署链路从开发态 `docker-compose.yml` 拆分出 `docker-compose.prod.yml`，`server-up.sh` 也同步调整为“安全预检 -> 迁移 -> 拉起服务”的正式版顺序
  - assistant 接口对未知异常的处理从“伪装成业务 unsupported 响应”改为记录日志并返回真实 `500`，避免线上监控、告警与前端错误语义失真

- 在纯 Docker 的正式环境模拟中，还额外暴露出一个迁移兼容性问题：
  - Alembic 默认 `alembic_version.version_num` 长度为 32，而当前 revision `0005_sync_runtime_schema_to_models` 超过了这一长度
  - 结果是在容器内首次全量迁移时，DDL 已执行但版本号写入失败，表现为 `api` 容器拉起前迁移卡死
  - 排障后确认这是正式环境演练中暴露出的迁移兼容性问题，而不是业务接口本身故障；修正数据库版本表后，最终以纯 Docker 方式完成了 `db -> migrate -> api/langgraph` 启动验证，并确认 `/openapi.json` 返回 `200`
- 这轮工作的标志意义是：项目开始从“功能已经可演示”进一步进入“团队细节可用、身份采集闭环、正式版具备基础安全门禁”的发布前阶段。

### 八、时间线页重构把“日历 / 费用”正式收口为统一读模型与统一界面

- 在 2026-03-28 这一轮后续设计和实现中，产品方向从“日程页 + 费用页并行”进一步收口为单一 `时间线` 入口：
  - tabBar 中原有“日历 / 费用”入口被合并为“时间线”
  - 页面认知从“两个模块切换”改为“同一天发生了什么”的统一时间流
  - 右上角最终收口为整页右下角悬浮控制：一个 `+` 创建按钮，一个筛选漏斗按钮
- 架构上没有直接合并底层业务表，而是新增“统一读模型”：
  - 后端新增 `timeline` 聚合接口，对 `schedules` 与 `finance_records` 做按天分组聚合
  - 前端统一消费 `kind / occur_at / day_key / title / amount / location / note` 等展示字段
  - 写操作仍保留原有 schedule / finance 创建、编辑接口，降低一次性重构风险
- 交互语义被重新定义为更贴近日常管理：
  - 左滑统一只保留“复制”，不再保留日程“已完成 / 未完成”状态切换
  - 日程编辑、费用编辑继续共用底部弹层，但视觉上改成更明显的 bottom sheet
  - 页面默认围绕“今天”使用，保留“回到今天”按钮
- 视觉与信息架构也经历了多轮连续收口：
  - 顶部大卡被继续压缩为固定单行，只保留“时间线 + 短说明 + 回到今天”
  - 左侧形成日期轨，右侧按天堆叠统一卡片
  - 同一天内卡片统一外壳，但用标签和金额颜色区分“日程 / 收入 / 支出”
  - 卡片中去掉“记录人”，压缩高度；费用第二行右侧从重复类型改为显示分类
  - 页面底部控制从卡片内移动到整页右下角悬浮，最终收口为两个纯圆形图标按钮
- 筛选与创建动作被有意识地做成同一套控制语言：
  - `+` 弹出“记日程 / 记支出 / 记收入”
  - 漏斗弹出“查日程 / 查收入 / 查支出”
  - 相关中文、英文、日文文案都被要求继续走 i18n，而不是写死在 WXML 里
- 地点与分类录入方式被从“选择器 / 地图能力”转成“快速文本录入”：
  - 地点不再依赖微信地图选点，而是改成文本输入 + 团队常用地点快捷列表
  - 费用分类也同步改成文本输入 + 快捷项，预设以城市上班族常见收入 / 支出类别为主
  - `chooseLocation` 相关权限与入口被移除，进一步减少平台能力耦合
- 在随后的发布前收口里，时间线页又继续做了一轮“把页面压回协调器”的模块化整理：
  - 原先写在 `schedule/index.js` 中的分类预设与翻译兜底被抽离，统一改为从 i18n 消息资源读取，不再保留页面内硬编码分类文案
  - 重复的翻译路径解析逻辑被收进共享 `translateMessage` 能力，`schedule` 与 `analysis` 两页改为复用同一套取词方式
  - 时间线页内部进一步拆出 `api`、`state`、`timeline`、`composer`、`composer-state`、`mutations`、`swipe` 等模块，把读模型适配、表单 payload、滑动手势和提交删除流程从主页面对象中下沉
  - 重构后 `schedule/index.js` 从接近千行收缩到六百余行，角色更接近“页面状态协调器”，而不是继续叠加业务细节的单文件子系统
- 时间线页还额外补上了“跨天快速跳转”的热力日历入口：
  - 左侧日期轨整块区域都可以点击，不再只依赖大号日期文字
  - 弹出月历以蓝色深浅表示某天记录密度，实现“热力图式”快速跳转
- 列表排序也在这轮被最终收口为符合自然时间感知的规则：
  - 日期从上到下按时间正序，过去在上，未来在下
  - 同一天内按开始时间从早到晚排序
  - 若时间相同，日程优先于费用；再按标题或分类字母顺序稳定排序
- 这一轮的工程意义在于：产品开始明确区分“统一展示模型”和“底层业务写模型”，同时把 i18n、UTF-8、一致交互语义与右手操作习惯一起纳入同一轮页面重构中。

### 九、这一段迭代的总体判断

如果说 2026-03-21 之前的主线是“把产品和编排系统搭起来”，那么这一段更像是进入了“高频使用细节与真实联调约束”的深水区：

- 前端从页面存在，进入到高频动作优先、手势语义明确、吸顶与弹层行为统一的产品化阶段。
- i18n 从“翻译资源存在”进入到“禁止页面遗留硬编码文案”的工程化阶段。
- 助手编排从“能回答费用问题”进入到“查询链路要支持结构化时间范围”的能力补齐阶段。
- 联调问题也第一次清楚地区分了“代码问题”和“宿主环境问题”的边界。

这一段历史的价值，在于它把 TeamHome 从“功能版”继续往“可持续维护、可长期演进的产品版”推进了一层。
